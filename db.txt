IBACOLOR DATABASE ENTITIES
=========================

Scope
-----
Minimal normalized schema for the entities used by the current portal.
MySQL/MariaDB design reference only; the PHP pages currently use browser
storage and are not connected to this database.

Use InnoDB, foreign keys, UTC timestamps, and prepared statements.
Store password_hash() output only. Never store passwords or confirmations.
Store uploaded files outside the database; keep only private file metadata here.


1. CORE APPLICATION ENTITIES
-----------------------------

barangays
  barangay_id       PK
  name              UNIQUE, NOT NULL

accounts
  account_id        PK
  email             UNIQUE, NOT NULL
  password_hash     NOT NULL
  role              ENUM('resident', 'admin')
  status            ENUM('active', 'pending', 'suspended')
  created_at

resident_profiles
  account_id        PK, FK -> accounts.account_id
  first_name        NOT NULL
  middle_name       NULL
  last_name         NOT NULL
  mobile_number     NOT NULL
  barangay_id       FK -> barangays.barangay_id
  address           NOT NULL
  profile_image_key NULL
  verification      ENUM('pending', 'verified')
  privacy_policy_version NOT NULL
  consented_at      NOT NULL

services
  service_id        PK
  code              UNIQUE
  name              NOT NULL
  description       NOT NULL
  category          NOT NULL
  office            NOT NULL
  status            NOT NULL
  fee_information   NULL
  processing_info   NULL
  instructions      NULL

service_requirements
  requirement_id    PK
  service_id        FK -> services.service_id
  requirement      NOT NULL
  display_order

service_requests
  request_id        PK
  reference         UNIQUE, NOT NULL
  account_id        FK -> accounts.account_id
  service_id        FK -> services.service_id
  details           NOT NULL
  status            NOT NULL
  submitted_at      NOT NULL
  updated_at        NOT NULL

request_status_history
  history_id        PK
  request_id        FK -> service_requests.request_id
  changed_by        FK -> accounts.account_id, NULL for system
  status            NOT NULL
  note              NULL
  changed_at        NOT NULL

request_documents
  document_id       PK
  request_id        FK -> service_requests.request_id
  uploaded_by       FK -> accounts.account_id
  document_name     NOT NULL
  storage_key       NOT NULL
  mime_type         NOT NULL
  review_status     ENUM('submitted', 'accepted', 'needs correction')
  review_note       NULL
  uploaded_at       NOT NULL

community_reports
  report_id         PK
  reference         UNIQUE, NOT NULL
  account_id        FK -> accounts.account_id
  category          NOT NULL
  barangay_id       FK -> barangays.barangay_id
  location_details  NULL
  description       NOT NULL
  observed_at       NULL
  frequency         NULL
  status            NOT NULL
  submitted_at      NOT NULL
  updated_at        NOT NULL

report_status_history
  history_id        PK
  report_id         FK -> community_reports.report_id
  changed_by        FK -> accounts.account_id, NULL for system
  status            NOT NULL
  note              NULL
  changed_at        NOT NULL

report_attachments
  attachment_id     PK
  report_id         FK -> community_reports.report_id
  uploaded_by       FK -> accounts.account_id
  file_name         NOT NULL
  storage_key       NOT NULL
  mime_type         NOT NULL
  uploaded_at       NOT NULL

public_contacts
  contact_id        PK
  name              NOT NULL
  type              NOT NULL (office, emergency, or hotline)
  telephone         NULL
  email             NULL
  address           NULL
  is_verified       NOT NULL

notification_preferences
  account_id        PK, FK -> accounts.account_id
  request_updates   NOT NULL
  announcement_updates NOT NULL


2. BLOCKCHAIN RECORDS — NOT DATABASE TABLES
--------------------------------------------

News and Announcements are intentionally excluded from the database entities.
For each published version, write a blockchain record containing:

  content_type      'news' or 'announcement'
  version           incremented for each published correction
  content_hash      SHA-256 hash of the exact published public content
  published_at      publication timestamp

Keep the public content itself in public file/content storage, not in the
relational database or on-chain. Verify it by hashing the retrieved version
and comparing it with the blockchain record. Drafts and private author data
are not blockchain records. A hash proves content integrity, not truth.
Blockchain integration is optional and is not implemented by the prototype.


3. WHAT NOT TO MAKE SEPARATE ENTITIES
--------------------------------------

- Sign-in and password confirmation are actions/validation, not entities.
- Municipality and province are fixed for this single-municipality portal;
  derive them from configuration rather than repeating them on every profile.
- Applicant name/contact details come from resident_profiles; do not copy
  them into each request or report.
- Registration GPS capture is not needed for the ongoing portal record; do not
  retain precise coordinates unless a separate justified use and consent exist.
- Categories, statuses, roles, and frequencies are fields here. Add lookup
  tables only if administrators need to manage those values dynamically.
- Request/report status history is retained because status changes need an
  audit trail. The main row's status is the current status.
- Uploaded file bytes stay in private file storage, not in these tables.
